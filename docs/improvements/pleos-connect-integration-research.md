# Hyundai Pleos Connect — integration research

Research notes on Hyundai Motor Group's **Pleos Connect** platform and what, if anything,
applies to Bloo. Written from the official Pleos Playground docs
(`document.pleos.ai` / `pleos.ai/playground`) as of the current docs revision.

## TL;DR for Bloo

There are **two separate Pleos products**, and only one is even theoretically usable by a
phone app like Bloo:

| Product | Where it runs | Control? | Usable by Bloo? |
|---------|---------------|----------|-----------------|
| **Pleos Connect SDK (Vehicle SDK)** | *inside the car* — an AAOS infotainment app on the head unit | Yes (lock, HVAC, windows, seats, lights…) | Only if Bloo ships an in-car AAOS app (different product) |
| **Vehicle Data API** (cloud, `api.pleos.ai`) | Cloud REST | **No — read-only** | Yes for *data*, but Europe-only and read-only today |

**Key finding:** as of this writing there is **no official cloud car-control (command) API**
in the Pleos platform. The Vehicle Data API retrieves telematics data only. Remote
lock/unlock/climate control remains in the reverse-engineered per-brand app APIs Bloo
already uses. The Vehicle SDK *does* control the car, but it runs **on the vehicle's
head unit** (Android Automotive OS), not on a phone.

## 1. Pleos Connect SDK (Vehicle SDK) — in-vehicle apps

Docs: `document.pleos.ai/en/api-reference/connect-sdk-pleos/`

- **What it is:** an integrated toolkit for building **infotainment applications that run in
  the Pleos Connect environment**, built on Google **Android Automotive OS (AAOS)**. It talks
  to a local *Vehicle Service* over IPC — there is no cloud round-trip and no remote access.
- **Modules:** Vehicle, NaviHelper, TextToSpeech, SpeechToText, ADAS, Fused Location.
- **Vehicle SDK domains (the control surface):** Brake, CarInfo, Display, **Door**,
  DrivingMode, EvBattery, Fuel, **HVAC**, Light, Odometer, Safety, Seat, SideMirror,
  SteeringWheel, Tire, Toll, TurnSignal, Window, Wiper.
- **Programming model:**
  - Entry point `Vehicle`; obtain domains via `getDoor()`, `getBrake()`, `getHvac()`…
  - Per domain: `checkXxxCapabilities()` (support + allowed ranges), `getXxx()` (read),
    `setXxx()` (write/control), `registerXxx()`/`unregisterXxx()` (callbacks).
  - Lifecycle: `initialize()` → use → `release()`; results are **async** via `onComplete`/
    `onFailed` lambdas (IPC), not synchronous returns.
  - Example control methods (Door): `setDoorLock`, `setDoorPosition`, `setGloveBoxLock`,
    with `getDoorLockState` + `registerDoorLockState` for reads/subscriptions.
- **Install:** Maven repo `https://nexus-playground.pleos.ai/repository/maven-releases/`,
  dependency `ai.pleos.playground:Vehicle:2.3.0`.
- **Permissions:** manifest `pleos.car.permission.CAR_*` (read) and
  `pleos.car.permission.CONTROL_CAR_*` (control), e.g. `CAR_DOORS`, `CAR_CLIMATE`,
  `CAR_ENERGY`, `CAR_SAFETY`, `CAR_SEATS`, `CAR_LIGHTS`. **App-review gated:** declaring an
  unapproved permission or calling its API fails review; permissions are pre-negotiated with
  the Pleos App Market.
- **Distribution:** via the **Pleos App Market** (in-car store), not the Play Store.
- **Emulator:** Pleos Connect Emulator + AVD, for development.

**Implication:** this is a *different app target* (an AAOS head-unit app), not a change to
Bloo's phone client. It is the only official route to on-car control, but it is not remote —
it works from inside the vehicle.

## 2. Vehicle Data API (cloud) — telematics data

Docs: `document.pleos.ai/en/api-reference/vehicle-data-api/`

- **What it is:** an open **read-only** REST API returning data generated by Hyundai/Kia/
  Genesis connected cars, within the owner's data-sharing consent.
- **Base:** `https://api.pleos.ai/v1/vehicles/{vin}/…`
- **Endpoints (all GET, read-only):**
  | Path | Data |
  |------|------|
  | `/batteries` | charging status, plug state, charge %, time-to-full |
  | `/powertrains` | engine / motor / battery status |
  | `/locations` | lat/lon, altitude, heading, speed |
  | `/driving` | engine start, cumulative mileage, parking state |
  | `/status` | doors/trunk, tire pressure, warnings, climate |
  | `/freezer` | (camping/accessory freezer) temp + state |
  | `/powertrains/data`, `/speed`, `/driving/data`, `/status/data` | raw source data |
- **Auth (OAuth2-style bearer):**
  - Private users: **My Vehicle API key** (clientId + clientSecret) →
    `POST https://api.pleos.ai/v1/auth/personal-token` with `Brand: hyundai|kia|genesis`
    header and `{clientId, clientSecret}` body → `data.accessToken`, then
    `Authorization` header on calls. Basic vehicle data available 24h after consent.
  - Business users: request access → approval → owner consent flow (Login API + redirect URL).
- **Regions:** **Europe only** as of Aug 2026 (long list of EU/EEA/UK countries). Other
  regions "in preparation". The private-user key issuance is Europe-only too.
- **No command endpoints.** No lock/unlock/climate-start — data retrieval only.

**Implication for Bloo:** this could become a *second, official data source* (status,
charging, location, tires, climate read) for European owners, alongside the existing
reverse-engineered per-brand APIs. It does **not** replace the command paths.

## 3. How this maps onto Bloo today

Bloo's `:shared` layer already abstracts per-brand telematics behind `VehicleRepository`
with one `repositoryFor(brand, …)` factory:

- `BlueLinkApi` — Hyundai/Genesis US (`api.telematics.hyundaiusa.com`), OAuth creds per brand.
- `KiaUsaApi` — Kia US.
- `EuApi` — Europe (Hyundai/Kia/Genesis EU).
- `CanadaApi` — Canada.

A Pleos **Vehicle Data API** client would slot in as another `VehicleRepository`
implementation (or a supplementary `StatusSource`), reusing:

- the same `Brand` model (Pleos `Brand` header is `hyundai|kia|genesis` — already modelled),
- the same `SnapshotStore` write path and `BlueLinkGate` serialization,
- the same `AppLog`/slow-body logging and `ResponseFraming` retry helpers.

But note the **consent + region + read-only** constraints mean it is an *additive* data
source for EU owners, not a control path.

## 4. Open questions / risks

- **No cloud control API** confirmed on the Pleos side yet — a genuine remote-control
  replacement for the app APIs does not exist here. If Hyundai later ships one, it would
  likely be a new Pleos API surface, not the Vehicle SDK.
- **Region lock:** Europe-only, which overlaps Bloo's existing `EuApi` coverage.
- **Ownership/consent:** data requires the owner's sharing consent; app-approval gating on
  the SDK side (App Market review) is incompatible with a sideloaded GitHub-Releases app.
- **SDK licensing/AAOS:** the Vehicle SDK is an in-car AAOS product; adopting it means a
  separate in-car app, a different store, and AAOS hardware — likely out of scope for Bloo's
  phone remote.

## 5. Recommendation

1. **Keep the current reverse-engineered command APIs** — they remain the only remote
   control path.
2. **Treat Pleos Vehicle Data API as a future additive status source** for EU owners
   (a `PleosVehicleDataRepository` behind the existing `VehicleRepository` abstraction),
   gated on the private-user key flow becoming generally available outside the Playground.
3. **Do not** attempt the Pleos Connect (Vehicle) SDK for Bloo — it is an in-vehicle AAOS app
   target, not a phone API, and its App Market review gate does not fit a sideloaded app.
4. Re-check `document.pleos.ai` periodically: if a Pleos **cloud command** API appears, it
   would be the first official remote-control path and worth a dedicated client + tests.
